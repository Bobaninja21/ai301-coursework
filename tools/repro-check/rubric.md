# Rubric: is this reproduction package ready to post?

Eight required checks, two preferred. The required eight are ordered by
the proof families the lecture named: the environment is recorded, the
steps are followable, something was actually observed, what was observed
is the issue's behaviour, the write-up claims no more than the artifacts
show, any deviation is admitted, the claim comment is this issue's, and
the words satisfy the repo's stated rules.

Two rules apply to every check below, and they are the whole method:

1. **Grade the thing, not the shape.** No check reads how many steps a
   report has, whether it uses the template's headings, how long it is,
   or how confident it sounds. Terseness is not a defect and polish is
   not evidence. Every pass condition asks about an outcome someone
   else could re-derive from the same text.
2. **A cannot-reproduce is a first-class result.** A report that
   honestly tried, failed, and says what differed passes every proof
   check it can pass. Only the claim of a result the artifacts do not
   show is a failure. The failure mode this rubric exists to catch is a
   confident report of the wrong behaviour, not a modest report of no
   behaviour.

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| `environment-recorded` | The environment record in the repro report (its `Environment:` line or block, or the equivalent stated inline in the steps), read against the environment the issue and its `bug reports` template name. | Passes when the report names, at minimum, the version of the software under test and the platform it ran on. Additionally, when the issue or the thread names a further axis the behaviour turns on — shell, browser, driver, backend, build profile, language setting, install method — the report must name its value on that axis, or say it could not match it. A cannot-reproduce report passes here on the same terms; naming the axis you differ on is the whole point. **Fails** when there is no environment record anywhere in the report, or when the one axis the issue says the bug depends on is simply absent. A record that is short passes: one line naming version and platform is a record. | required |
| `steps-rerunnable` | The steps section of the repro report, plus any inputs it references (files, configs, commands, fixtures, links), read against what the issue itself already supplies. | Passes when a stranger holding only this report and the issue could get from a stated starting state to the trigger: every input the run needs is pasted inline, quoted from the issue, generated by a command that is given, or fetched from a public source that is named. **Fails** when any input the run depends on is private, unshared, or described only in prose the reader cannot execute — "our internal config", "our monorepo", "set up the project", "configure it as usual" — or when a step the issue names as necessary to the trigger is missing from the sequence. Reusing the issue's own steps verbatim is a pass, not a shortcut. | required |
| `evidence-shown` | The body of the repro report: is there any transcribed observation in it — a command with its output, a log excerpt, a stack trace, a rendered result, a screenshot described in words — as opposed to statements about what happens. | Passes when at least one concrete observation produced by the attempt is shown in the report. **Fails** when the report only asserts: outcomes ("it reproduces every time"), diagnoses ("this is a debounce race"), or certainty ("guaranteed reproducible", "I verified this") with nothing observed pasted anywhere. This check does not ask whether the artifact is the *right* one — `artifact-shows-the-issue` does that. It asks only whether anything was looked at. | required |
| `artifact-shows-the-issue` | The shown artifacts read side by side with the behaviour the issue describes: the exact trigger the issue names (its syntax, flags, input values, range, sequence) against the command or action that actually produced the artifact, and the issue's reported symptom against the symptom in the output. | Passes when at least one shown artifact was produced by the trigger the issue names and displays the symptom the issue reports — **or**, for an explicit cannot-reproduce, was produced by that same trigger and displays the symptom's absence. **Fails** when the run departs from the issue's trigger (a different expression, a different argument form, a modified input, a different code path) so that the output is a different failure mode than the one reported — a graceful validation error standing in for a crash, a compile error standing in for a runtime error — or when the artifacts show only that the software ran (a version banner, a session list, a screen that loaded) and nothing that bears on the reported behaviour. A different failure mode is a different bug, however real it is. | required |
| `outcome-matches-evidence` | The result the report states, and the certainty language in both the report and the claim comment, held against what the shown artifacts actually display. | Passes when the confidence asserted is no greater than the artifacts support. An explicit "I could not reproduce this", backed by what was run and what was seen, passes in full. **Fails** when the write-up narrates an artifact as showing something it does not (calling a still-running terminal a crash, calling an argument error an overflow), asserts a cause or a scope no shown output reaches ("confirmed on all platforms", "this also affects the Store build", "I verified the race condition"), or states an expected/actual pair that contradicts the output pasted above it. The test is directional: claiming less than the evidence shows never fails; claiming more always does. | required |
| `deviations-disclosed` | The report's environment record and steps compared against the conditions the issue and thread name as the affected ones: the version the issue was filed and confirmed against, the platform, the install method, and the input the issue supplies. | Passes when there is no material difference, or when every material difference is named in the report. Naming it is enough — "filed against 13.0.0, unchanged on 15.2.0", "the report is macOS + fish; I am on Linux + zsh", "matches the report on a different OS and install method" — no justification is required. **Fails** when a material difference exists and the report is silent about it. The difference that matters most is version: testing an older release than the one the issue is confirmed on, without saying so, turns that release's behaviour into false evidence about the reported bug. | required |
| `claim-is-specific` | The claim comment read against this issue's body and thread. | Passes when the comment names something only this issue has — the misbehaviour in the reporter's terms, the file, function, flag or version at stake, the thread pointer being followed, or the concrete next thing to be looked at — so that pasting it unchanged under a different issue would make it wrong; **and** it commits only to investigating and reporting back. **Fails** when the comment is interchangeable ("I'd like to work on this", "great project, assign me"), is a bare confirmation with no stated intent ("+1", "same here"), demands assignment or reservation, or promises an outcome the writer cannot guarantee: a fix, a deadline, a date, "within 2 days", "I'll have a PR up tonight". Warmth is not the failure and brevity is not the failure; substitutability and over-promising are. | required |
| `repo-conventions-met` | The `contribution policy` line and the `bug reports` template line in the Repo facts block, read against what the claim comment and the repro report actually contain. Live mode: `CONTRIBUTING.md`, any linked AI policy file, and the issue template. | Read the policy for requirements that land on a **comment**, and check the comments against those and only those. **Fails** when the policy requires AI assistance to be disclosed and neither comment discloses it. Treat the package as AI-assisted work: these comments are drafted with an assistant, so a disclosure requirement is live even when the text never mentions a tool, and silence is non-compliance rather than an absence of obligation. **Passes** when the policy is silent on AI; when it is permissive or conditional without asking for disclosure on comments (be responsible for your contribution, understand and test every change, low-quality AI content is closed, disclosure asked only in the pull request); when it requires comments to be in the contributor's own words and the comments read as one person's own writing rather than generated boilerplate; or when the policy does ask for disclosure and a comment states it, naming the tool and the extent of the help. A template's asks (version, OS, steps, expected, actual) are graded here only as the repo's stated wants, and only when a comment omits something the template names outright; the proof checks above already own whether the content is sufficient. | required |
| `control-run-shown` | The artifacts: is a contrasting run present — the same command with the trigger removed, the neighbouring input the issue says behaves correctly, or the configuration the issue says works. | Passes when a control is shown and its result differs from the failing run in the direction the issue predicts. This is the difference between "I saw a bad output" and "I isolated what causes it", and it is the single strongest thing a first-time reporter can add. It never gates: plenty of faithful reproductions have no meaningful control to run. | preferred |
| `next-step-named` | The claim comment's stated next action. | Passes when the comment names a concrete place the writer will look next — a file, a function, a linked issue or PR, a hypothesis to test — rather than an intention to "start working on it". On an accepted package this is the line that tells a maintainer whether to spend a reply on you. | preferred |

## Verdict rule

**`accept` if and only if every `required` check grades `pass`.** Any
required `fail` gives `reject`. There is no third verdict.

`unclear` counts as `fail` on a required check. A reproduction package
is a proof, and a proof whose evidence I cannot locate has not been
shown to me; the package goes back to its author either way, which is
what `reject` means here — hold, not condemn.

Reserve `unclear` for the case where the evidence line a check names is
genuinely missing from the package. Note that `environment-recorded`,
`evidence-shown`, `artifact-shows-the-issue` and `claim-is-specific`
cannot come back `unclear` in practice: the absence each one looks for
*is* the fail. `deviations-disclosed` and `repo-conventions-met` are
written as rebuttable passes — they pass unless a named disqualifying
fact is present — so a silent policy or an unchanged environment is a
`pass`, never an `unclear`.

`preferred` checks never change the verdict. Report their grades: on an
accepted package they are what makes one reproduction more useful to a
maintainer than another, and in live mode they are the two things worth
adding to a draft that already passes.
